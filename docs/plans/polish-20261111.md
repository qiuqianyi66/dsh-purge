## 第五批：F7 断网诊断修真实缺陷（1.1.87）

- **复现手法（不真断网）**：进程内把 `https.request` / `http.request` 打桩成 `ENOTFOUND`、`fetch` 抛
  `fetch failed`，再调用真实的 `checkUpdate()`。这是网络层替身，代码路径、状态读取、诊断生成
  全走真身，唯一被替换的是 socket。
- **修复前**：`{"ok":true,"hasUpdate":false,"remoteVersion":"1.1.86","via":"dsh"}` —— 断网被读成
  「已是最新」。根因两处：
  1. `describeLane` 的 `hasRemote: Boolean(sha || versions.length)` 把本地条目
     （`ensureRunningVersion` 注入的 `kind:"local"`）和历史缓存（`kind:"history"`）也算成远端证据，
     于是 `lanes.stable.hasRemote` 恒为真，`checkUpdate` 不会抛错。
  2. 即使抛错，`remoteHeadSha` / `listGithubTags` 各自 `catch → ""`，抛出的消息只有
     「无法读取 GitHub main」，分类器无关键词命中 → `stage=unknown`。
- **修复**：新增 `laneHasRemote(sha, versions)`（只认 `head` / `tag` 或远端 head sha）；
  `fetchRes` 失败时记 `_lastNetError`；`checkUpdate` 在网络全失败时带真实原因抛
  `无法读取 GitHub main：getaddrinfo ENOTFOUND api.github.com`；分类器补 `getaddrinfo`
  （覆盖 `ENOENT`/`EAI_AGAIN`）与中文「网络/连不上/连接失败」，并确认文件缺失类
  `ENOENT: no such file` 不误判成网络。
- **修复后**：`stage=network / reason=network-or-tls`，诊断片段含真实错误、`localVersion` 上下文，
  且本机路径已脱敏；联网回归 `hasRemote=true`、`head:1.1.86 / tag:1.1.86 / 1.1.85 / 1.1.84`。
