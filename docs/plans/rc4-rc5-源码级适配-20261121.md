# rc.4 / rc.5 源码级适配：上游到底改了什么，我们要不要动

> 用户要求「去仓库看源码，看更新了哪些，然后适配」。
> 取证方式：① 本地两棵隔离树 `src/` + `lib/` 逐文件 SHA-256 比对（比 GitHub API 准且不受限流）；② 从 npm 拉一份**完整 338 包** rc.5 树（与真机包数一致）；③ 官方随包发布的 `docs/upgrade-guide/`。
> 时间 2026-11-21。所有数字可复现，命令见第 7 节。

## 0. 结论先行

1. **rc.4 相对 rc.3 只改了一件事**：base 组合不再固定 `web.searchProvider`，改由 `dsh-web` 按模型路由选（DeepSeek 模型走 legacy Messages 搜索）。官方有条目 `v0.2.2-rc.4/web-search-deepseek-model-default`。
2. **rc.5 没有 upgrade-guide 条目**（官方 docs 里根本没有 `v0.2.2-rc.5` 目录），但源码确实改了：`dsh-llm` 新增错误码 `CONTENT_REFUSED`，`dsh-llm-deepseek` 新增 `refusal()` 处理 —— `stop_reason === 'refusal'` 时**先把 usage yield 出去**（已消耗 token 要计费），再抛错，并把 `stop_details.explanation`（如 blocked images）透传进错误文本。
3. **82 条补丁里，没有任何一条需要改 pattern**。rc.4/rc.5 触碰的 4 个补丁载体（`dsh-tool-web`、`dsh-llm-deepseek`、`dsh-base/cordis.patch.yml`、`dsh-refusal` 相关）逐条实测命中且二次 apply 幂等。
4. 由此完成适配落地：`dshTargets` 增加 `0.2.2-rc.5`（插件不再把 rc.5 判为不支持的宿主），矩阵仍保留 rc.3 为唯一 `supported`，rc.5 记 `compatible-isolated` 并补齐完整树证据。

### 1.2 rc.4 官方原文（`v0.2.2-rc.4/web-search-deepseek-model-default/guide.zh.md`）

> 「过去，共享的基础组合把 `web.searchProvider` 设为 `deepseek-search-api`……现在基础组合不设置 `searchProvider`，由 `dsh-web` 按模型提供方路由选择。为 `deepseek-official` 或 `deepseek-account` 路由上的模型请求发起的搜索使用 `deepseek-official` 搜索提供方……其他路由上的搜索，以及不服务于模型请求的搜索，仍使用 `deepseek-search-api`。」

影响面：**只影响没有显式设置 `web.searchProvider` 的部署**。本插件从来没碰这一行，所以插件用户会直接吃到上游新默认。想锁回旧行为不用改插件，按官方 guide 第 2 步在 `@deepseek-ai/dsh-web` 的 config 里写 `searchProvider: deepseek-search-api` 即可。

### 1.3 rc.5 的真实变化（无官方 guide，属源码实证）

```ts
// dsh-llm/src/error.ts —— 新增一个错误码（rc.3 完全没有）
CONTENT_REFUSED: {},

// dsh-llm-deepseek/src/translate.ts —— 新增
function refusal(details: unknown): LlmError {
  const explanation = typeof details === 'object' && details !== null && 'explanation' in details ? details.explanation : undefined
  return new LlmError(`DeepSeek refused to answer under its content safety review${...}`, 'CONTENT_REFUSED')
}
// 流里：refusal 时先 yield usage，再 throw（注释原文：Tokens consumed before a refusal are billed, so report them before failing.）
```

对本插件的意义：**这是上游首次把"拒答"变成一等公民错误码 + 会计入 token**。对红队评测来说是好消息——拒答不再伪装成 malformed response，观测口径更干净。但**不改变任何补丁写法**：我们没有替换 refusal 相关的 `MALFORMED_RESPONSE` 文案，也没有依赖 `stop_reason` 的旧映射。

> 附带纠正一条旧说法：此前记录「rc.3 guide `deepseek-refusal-code` 把 refusal 从 MALFORMED_RESPONSE 改成 CONTENT_REFUSED」不准确。源码实测 rc.3 的两处文件里 `CONTENT_REFUSED` **一次都不出现**，它在 rc.5 才被引入。

## 3. 本轮做的适配改动（不是改补丁，是改「能不能装 / 怎么记账」）

1. **`package.json` `dshTargets` 增加 `0.2.2-rc.5`**。`HOST_TARGETS` 读这个数组，决定插件是否把该宿主判为「已适配目标」。不改这一行，用户装了 rc.5 后插件会把它判成非目标版本 —— 适配等于没做。`dshTarget` 仍保持 `0.2.2-rc.3`（主目标），矩阵里也仍只有一条 `supported`。
2. **`DSH_RELEASES` 的 rc.5 行补完整树证据**（`fullTree`：338 包 / applied 55 / reverted 46 / drifted 0），并写明「无一条 pattern 受 rc.4/rc.5 影响」。
3. **修了 `audit-next` 的审计口径缺陷**：正则型 pattern 此前被直接跳过（`matched += 0`），导致 `#40`、`#73` 这两条纯正则补丁**无论官方文本多吻合都永远落 unknown**。改为对 RegExp 取 `source`+`flags`（去掉 `g`）判存在性。实测差异**只有 2 条**：#40 `unknown 0` → `ok 1`、#73 `unknown 0` → `ok 1`，无其他补丁被误升。
4. **把 `#40` 的跨行正则锚点纳入 rc.5 fixture**：`fixture.systemPrompt.assemble`（从 `const transformed = await this.ctx.waterfall(...)` 到 `contexts: runtimeContextSuppressed ?` 之后再带 2 行），`test/anchor-rc5.test.js` 增至 **8 条**，其中 #40 断言「命中 + 幂等 + 打完仍保留 `tools`」。
5. **新增 `scripts/upstream-src-diff.mjs`（`npm run upstream:diff`）**：下次升级先跑它，就知道上游改了哪些包，而不用等人肉读 diff。
