## 2. #9 为什么不能原生化（源码级证据）

`dsh-user-approval/src/index.ts`：

- L296-301 官方注释写明「The 'never' policy is decided HERE, before any dispatch: a listener cannot override it」，紧接 `if (this.effectivePolicy(session) === 'never') return 'rejected'`；派发 `'approval/request'` 在 L308，**在其后**。
- 本插件 #8 把 base 组合的 approval 默认策略改成 `danger-full-access → never`，#10 把包内 Config 默认也改成 `never`。所以插件自己的默认态恰好落在监听器管不到的分支上。
- 想绕开就得把策略改回 `ask`，但那会把模型可见句子从 `NEVER_SENTENCE` 换成 `ASK_SENTENCE`（「without an available answerer, the request fails closed」），与 #11 想传达的「自动放行、尽管申请升权」相反 → 提示词语义不等价。
- 该句子是具名 prompt context `approval:policy`，官方允许**按 agent 作用域同名 shadow**（`dsh-system-prompt/src/index.ts` L479/L516：scoped 覆盖 global，同层重名抛错）。但注册时机需要早于提示词装配，本机只找到 `agent/pre-step` 这一个 per-agent 钩子，**是否足够早未验证**。
- 另有一层耦合：`permission` 行的 presets 表里 `danger-full-access` 自带 `approval: never`，即便改了 approval 行 config 也会被预设拉回 never。

结论：#9 要原生化必须**整簇迁移 #8/#10/#11 + 预设表**，且依赖一个未验证的 shadow 时机。按门 2 提案第 5 条第 4 款，直接交付不等价证据，不硬推。

## 5. G4 失败的根因（已定位并**已修复**）

**#7 / #8 其实 apply 成功，是 diagnose 误判。** 一条命令复现：

```powershell
node scripts/audit-next.mjs --version 0.2.2-rc.3 --refresh
node scripts/f6-drift-probe.mjs on
```

实测输出：`#7 status=applied applied=1 drifted=0`、`#8` 同；文件里实际内容已是 `'danger-full-access'`；但 diagnose 报 `DRIFT #7 · base markers_ok=false marked=0`。

机制（三处代码事实）：

1. `lib/drift.js` 的 `markersPresent()` **只读 `patch.markers`（数组）**；而 #7 / #8 只定义了 `marker`（单数），#21 两个都没有 → 它们的 `markers_ok` **恒为 false**。
2. 于是判「已打」落到 `appliedEvidence = Boolean(row.diff) || row.marked > 0 || …`，实际起作用的是 `row.marked`＝文件里 `dsh-purge` 字样出现次数。
3. base yml 原生不含 `dsh-purge`（实测 0 次），**唯一往里写 `[dsh-purge]` 字面量的是 #63**。#63 一被跳过，#7/#8 就失去了这份「借来的证据」。

**这是既有诊断口径的缺陷，不是本次迁移引入的**：现网只要 #63 因 `skipIfMarked` 被跳过、或上游改了 plan-mode 文案导致 #63 失配，#7/#8 就会被误报 drifted。反过来更危险——只要 #63 在，#7/#8 哪怕真没打上也会被算成「已打」，属**假绿**。

### 5.1 修复（2026-11-21，用户批准后执行）

改 `lib/drift.js`，把 marker 口径收成一个函数，让诊断侧与 apply 侧（`core.js` 的 `patchApplied()`：markers 数组 > marker 单数 > replace 首行）对齐：

- 新增 `patchMarkers(patch)`：`markers` 数组优先，为空则回落到单数 `marker`。
- `markersPresent()`、`selfMarkedMarker` / `companionMarker` 三处判定统一改用它。

**为什么不是给 #7/#8/#21 补 `markers` 数组**：先用 `scripts/marker-audit.mjs` 全量盘过——只有 **6 条**补丁用单数 marker（#6/#7/#8/#10/#15/#16），且**全部**满足「marker 由补丁替换体写入」，官方基线不可能自带（如 #7 的 `'workspace-write'` vs `'danger-full-access'`）。所以兼容单数是安全的，不会引入新假绿；补数据反而是绕过口径缺陷、留下两套事实源。#21 本来就没有 marker，靠 `softSettle` 判 `satisfied`，不受影响。
