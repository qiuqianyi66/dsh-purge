## 2. 三个改变格局的上游事实

### 2.1 官方现在随包发布源码与文档（最大利好）

commit `38c7a9fb` `feat(release): publish package source, declaration maps, and documentation`：每个发布成员发布 TypeScript `src/`、declaration maps，`@deepseek-ai/dsh` 发布整个 `docs/`（含全部 upgrade-guide），并给 shell 调用注入 `DSH_INSTALL_DIR` / `DSH_NODE_EXECUTABLE`。

本机实测：**335 / 338 个包带 `src/` 目录**；`@deepseek-ai/dsh/docs/upgrade-guide` 存在。

影响：F1–F3 那套「读 bundled `lib/index.js` + `.dshpurge.bak` 反推官方原意」的做法可以退役一半——直接读官方 TypeScript 源码，pattern 也能按源码结构生成，而不是猜编译产物。

### 2.2 `capability-seams` 揭示了我漏掉的一整层迁移手段

官方把服务分成 `core` / `seam` / `bundle` / `service`。**`seam` 意味着实现可整体替换**，而我此前只考察了「包内有没有 Config 字段」，漏掉了「换掉整个 provider 行」。

| 服务 | 类别 | 官方实现 | 对 dsh-purge 的意义 |
| --- | --- | --- | --- |
| `ctx.approval` | **seam** | user-approval | 官方原文：决策走 `approval/request` waterfall，answerer 就是 listener，缺席 fail-closed → **#9 原生化得到官方文档背书**（此前只有源码证据） |
| `ctx.sandbox` | **seam** | sandbox-local / sandbox-ssh | #6 / #15 可通过替换 sandbox provider 实现，不必改 Seatbelt 常量 |
| `ctx.fs` | **seam** | fs-local / fs-sandbox / fs-ssh | #16 可通过组合 `fs-local` 取代 `fs-sandbox` 实现 |
| `ctx.shell` | **seam** | bash-local / bash-sandbox / pwsh-local | 沙箱与执行器可分离替换 |
| `ctx.llm` | **seam** | llm-deepseek / llm-pi-ai / **llm-replay** | **官方自带 replay provider**（test-support）→ 评测层可不再手写 transcript |
| `ctx.subagents` | **seam** | spawn / fork / acp / codex / claude-code / dsh-sdk | 子代理后端可换 |
| `ctx.sessionLogDeepSeek` | core | session-log-deepseek | 官方原文：**插件可注册 caller-owned exclusions** → #52 有比改 Config 更细的 API |

另外 base 组合里 **`fs-observation-policy` 默认 `disabled: true`** → #17 的诉求上游已默认满足，属可退役。

## 3. 对 F3b 结论的修正（不改已验证数字，只加候选层）

F3b 判的 40.0%（26/65）是**「零成本原生」**口径：只算 Config / composition / 具名 section / waterfall。这个口径仍然成立。

漏掉的是**第二层：seam 替换**。把官方 provider 行 `disabled` 再 insert 自己的实现，是官方支持的组合操作，但它意味着**你要自己维护一份官方工具/提供器的实现**。

| 层 | 手段 | 载体估算 | 维护成本 |
| --- | --- | --- | --- |
| T1 零成本 | Config 值 / composition 行 / section shadow / waterfall | **26/65 = 40.0%（已验证）** | 最低，升级基本免疫 |
| T2 seam 替换（候选，未验证） | 换 sandbox / fs / shell / llm provider；停官方 tool 行改注册自有 tool | 乐观可再覆盖 sandbox-local、fs-sandbox、tool-bash、tool-pwsh、tool-web(+nested)、llm-deepseek、pi-ai-* 等，**上限约 50%–60%** | **高于打补丁**：等于接管官方工具实现，每次上游改功能都要跟 |

**这就是关键取舍**：T2 能把百分比推上去，但把「82 条 pattern 的维护」换成「若干官方工具的分叉维护」，后者更贵。所以**不建议为了凑 60% 而做 T2**；建议只在这些情形用 T2：官方缝天然存在且实现很薄（如 fs-local 替 fs-sandbox、sandbox provider），或评测需要（llm-replay）。

## 4. 建议的演进路线（领先，而不是追）

**主张：把「领先」定义为「上游发版当天就知道哪条会坏、并且有可复算的判定」，而不是「补丁比上游改得快」。**

- **E1 上游雷达（新增，最高优先）**：定期拉 master 的 `docs/upgrade-guide/*` 与 merge commit 标题，与 82 条台账做交集，产出「本次上游变更命中哪几条补丁」。因为官方已发布 upgrade-guide，这件事可机械化，不需要人读 changelog。
- **E2 源码化 pattern（改造 F1/F2）**：改为基于随包 `src/*.ts` 生成与校验 pattern，编译产物只作落地目标。降低 rc 漂移导致的 pattern 失配。
- **E3 T1 全量迁移（F6 扩面）**：26 个载体走 Config/composition，保留补丁 fallback。这是唯一「越迁越省」的部分。
- **E4 评测层接官方观测（改造 F4/F5）**：`CONTENT_REFUSED` 作为拒答判定；`llm-replay` 作为回放 provider，替代手写合成 transcript；`approval/request` waterfall 作为审批观测点。
- **E5 T2 只做两处**：`fs-sandbox → fs-local`（纯组合，零实现）与评测用 `llm-replay`。其余 T2 不做。
- **E6 退役清单**：#17（上游默认已 disabled）、#2/#3/#14/#46/#54/#56/#77/#88（已 retired/空）——共 9 条可直接从活跃台账移出。

对 F7/F8 的影响：
- **F7 常驻 PoC** 应先做 E1 雷达 + E4 官方观测，再做 watcher；否则跑出来的报告仍依赖正则判拒答，不可靠。
- **F8 上游提案** 有了真实缺口清单：`ctx.approval` 已是 seam（不必提），真正缺的是**工具描述文案的 Config 化**（#33/#48/#29 等 no-hook 的根因）与**桌面壳退出/更新的可插拔处理**（#45/#82/#83/#84）。这两条才是值得提的 issue。

## 7. 实测修正（2026-11-21）：rc.5 离体审计推翻「pattern 追不上」的判断

雷达做完后，直接用既有 `audit-next` 把官方 **rc.5** 包树铺到隔离目录逐条试补丁（未升宿主、未碰真机）：

```powershell
node scripts/audit-next.mjs --version 0.2.2-rc.5 --json upstream-reports\audit-rc5.json
```

实测（退出码 0）：

| 项 | 数 |
| --- | --- |
| 落地载体键 | 45 |
| 参与审计补丁（不含退役） | 78 |
| 认得 | 56 |
| 校验型（只验 marker） | 6 |
| **需重对齐** | **0** |
| 未审计（载体不在 npm 包内） | 11 |
| 部分命中（含旧版本保留 pattern，属预期） | 22 |

**结论修正**：跨两个 rc（rc.3 → rc.5）**没有一条补丁的 pattern 失配**。第 1 节「靠 82 条字节 pattern 追版本永远落后」这个判断，就 pattern 层面而言**被实测否掉了**——上游这两个 rc 没有改动补丁锚定的原文。

真正的风险不在字面量，而在**语义**：`workspace-write` 边界跟随工作目录、`CONTENT_REFUSED` 拒答码、subagent 模型选择改为每次读 Host 设置——这些都不让 pattern 失配，但会让补丁「打上了却不再是原来的效果」。

所以战略重心要挪：**E4（评测层接官方观测）优先级高于 E2（源码化 pattern）**。E2 的收益被实测证明低于预期，E4 才是唯一能抓住语义漂移的手段。

### 7.1 雷达与审计的分工（实测校准，别把雷达当判定）

雷达预测「6 条变更命中 12 条补丁」，把这 12 条拿到 rc.5 审计里对照：

| 补丁 | rc.5 实测 |
| --- | --- |
| #69 #72 #78 #85 #86 #23 #26 #70 | `ok`（全部认得） |
| #80 | `verify`（校验型） |
| #73 | `unknown`（载体不在 npm 树） |
| #56 #77 | 已退役，不在审计范围 |

**雷达命中 ≠ 会坏**。雷达算的是「上游变更触达了哪些补丁的载体包」，是**注意力缩小器**；判「会不会坏」必须靠 `audit-next` 的逐条匹配。两者串联才是完整能力：

- `npm run upstream:radar -- --remote` → 上游改了什么、触达哪些补丁（含语义变更，pattern 匹配抓不到的那类）
- `npm run audit:next -- --version <新版本>` → 这些补丁的 pattern 还认不认得新原文

### 7.2 本次仍未覆盖的面（不得当结论）

- rc.5 的语义变更未逐条比对，只抽了与补丁强相关的几条。
- 未升宿主：本机仍是 rc.3，以上全部是离体结论。
